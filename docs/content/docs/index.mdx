Chronicle is a Go library that records every event into a hash chain (SHA-256, or HMAC-SHA256 when you key it), so edits and deletions show up when you verify. It is designed for multi-tenant SaaS applications that need SOC2, HIPAA, or GDPR compliance out of the box.

Chronicle is a library, not a service. You bring your own database, HTTP server, and process lifecycle. Chronicle provides the audit plumbing.

## What it does

- Hash chain integrity: every event is linked to the previous one. A changed or deleted event breaks the chain, and `VerifyChain` reports it. The plain SHA-256 chain catches corruption and accidental edits; key it with HMAC and add signed checkpoints to resist someone who can write your database.
- GDPR crypto-erasure: per-subject AES-256-GCM encryption. Delete the key, the data becomes irrecoverable, but the hash chain stays intact.
- Multi-tenant scoping: events and queries are scoped to the app and tenant on the context.
- Compliance reports: generate SOC2 Type II, HIPAA, EU AI Act, and custom reports. Export to JSON, CSV, Markdown, or HTML.
- Pluggable stores: PostgreSQL, SQLite and MongoDB on a Grove `*grove.DB`, Redis on Grove KV, and in-memory for tests. All implement the same composite `store.Store` interface.
- Sinks: stdout, file, S3, or custom. Retention archives expired events through one before it purges them. `Record` doesn't write to sinks.
- Plugin interfaces: `BeforeRecord`, `AfterRecord`, `AlertHandler`, `SinkProvider` and more, with a registry you call yourself. `Record` doesn't call them yet.
- Retention policies: automatic archival and purge with configurable schedules.
- Admin HTTP API: 24 endpoints for events, verification, checkpoints, erasure, retention, compliance and stats, guarded per operation class.
- Forge integration: drop-in `forge.Extension` with DI-injected `chronicle.Emitter`.

## Design philosophy

Chronicle is a set of Go packages you import. You control `main`, the database connection, and the process lifecycle.

Every subsystem defines a Go interface. Swap any storage backend with a single type change.

Each subsystem has its own store interface. The aggregate `store.Store` composes them all. One backend satisfies every subsystem.

It's append-only by design. There is no `UpdateEvent` or `DeleteEvent`. Compliance and hash chain integrity depend on immutability.

All entities use type-prefixed, K-sortable, UUIDv7-based identifiers, so an `erasure_` ID passed where an `audit_` ID is expected fails to parse.

## Quick look

```go
package main

import (
    "context"
    "fmt"
    "log"

    "github.com/xraph/chronicle"
    "github.com/xraph/chronicle/audit"
    "github.com/xraph/chronicle/scope"
    "github.com/xraph/chronicle/store"
    "github.com/xraph/chronicle/store/memory"
)

func main() {
    ctx := context.Background()
    ctx = scope.WithAppID(ctx, "myapp")
    ctx = scope.WithTenantID(ctx, "tenant-1")

    mem := memory.New()
    adapter := store.NewAdapter(mem)

    c, err := chronicle.New(chronicle.WithStore(adapter))
    if err != nil {
        log.Fatal(err)
    }

    // Record an event.
    err = c.Info(ctx, "login", "session", "sess-001").
        Category("auth").
        UserID("user-42").
        Meta("provider", "okta").
        Record()
    if err != nil {
        log.Fatal(err)
    }

    // Query events.
    result, err := c.Query(ctx, &audit.Query{Limit: 10})
    if err != nil {
        log.Fatal(err)
    }
    for _, ev := range result.Events {
        fmt.Printf("[%s] %s %s/%s\n", ev.Severity, ev.Action, ev.Resource, ev.ResourceID)
    }
}
```
